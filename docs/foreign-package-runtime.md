# Foreign-Package Runtime (C3)

This document describes the runtime architecture for foreign-distro
packages (apt/dnf/pacman) consumed via Reprobuild's content-addressed
store. It complements:

* [Linux-Third-Party-Distro-Packages.md](../Linux-Third-Party-Distro-Packages.md)
  (high-level design).
* [Linux-Third-Party-Sandbox-MVP.milestones.org](../Linux-Third-Party-Sandbox-MVP.milestones.org)
  (sandbox primitives, closed 2026-06-11).
* `ReproOS-Generations-And-Foreign-Packages.milestones.org` Phase C
  (harvesting + realize-time integration).

C3 ships:

* `apps/reprobuild-sandbox-launcher/launcher.c` -- the native
  user-namespace + bind-mount launcher (Linux); a no-op stub on
  Windows.
* `libs/repro_local_store/src/repro_local_store/sandbox_manifest.nim`
  -- realize-time manifest generator that walks the C2 catalog graph
  and emits a deterministic launcher manifest.
* `apps/reprobuild-sandbox-launcher/MANIFEST-FORMAT.md` -- the
  manifest file format.

## Architecture

```
                       harvest time                  realize time
                       (Phase C2)                    (Phase C3)
                                                   /---->  $prefix/launcher.manifest
                                                   |       (bind set + exec= path,
                                                   |        deterministic byte order)
                                                   |
recipes/catalog/foreign/apt/git.json  ->  walkCatalogGraph
       \-- dep_closure: [libc6, ...] -/  (libs/repro_local_store/
                                          sandbox_manifest.nim)         per-binary shim
                                                                       $prefix/bin/git
                                                                       (`exec` launcher)
recipes/catalog/foreign/apt/libc6.json
       \-- dep_closure: [libgcc-s1, ...] /

                                                            run time
                                                            (operator)
                                                            ----------
                                                            $ git --version
                                                              |
                                                              shim -> launcher
                                                                       |
                                                                       unshare(NEWUSER|NEWNS)
                                                                       mount(MS_BIND, ...) x N
                                                                       execve("$prefix/.../git", argv)
```

## Catalog graph walk

The C2 harvester emits one catalog file per package in the harvest
union. Each catalog carries ONLY its own per-record transitive
`dependency_closure`. The launcher's realize-time generator MUST walk
the catalog graph rooted at the package being installed -- it cannot
just read one root catalog's `dependency_closure` because:

* A future dnf/pacman harvester MAY emit non-transitive closures
  (immediate deps only); the consumer-side walker handles both.
* Composing two roots in one home profile (`git` + `vim`) means each
  binary needs its OWN root's closure -- separate per-root walks, not
  the harvest union.
* Per-record closure keeps the recursive `CacheEntryKey` composer's
  depth bounded.

See `walkCatalogGraph` in `sandbox_manifest.nim` for the
implementation. Failure modes:

* `CatalogResolveError` -- a dep file is missing under the catalog
  root. The walker hard-fails so the launcher never produces a hollow
  bind-set.
* `CycleDetectedError` -- the dep graph contains a cycle. apt cycles
  are rare but possible (mutually-recommending packages); we treat
  them as a hard error so the manifest is well-defined.

## Manifest format

The launcher reads a small line-oriented text format. See
[MANIFEST-FORMAT.md](../apps/reprobuild-sandbox-launcher/MANIFEST-FORMAT.md).

Determinism contract: identical inputs produce byte-identical
manifest text. The generator sorts the bind set by
`(target, source, flags)`; the writer normalizes path separators to
`/` so Windows-tested manifests parse cleanly under MSYS.

## Per-binary shim

For each binary in a foreign package's `bin/`, the realize pipeline
emits a tiny shim at `$prefix/bin/<binary>`:

```sh
#!/bin/sh
# Auto-generated by repro_local_store/sandbox_manifest.nim
exec /path/to/reprobuild-sandbox-launcher \
  --manifest=$prefix/launcher.manifest \
  --exec=/actual/store/path/to/<binary> \
  -- "$@"
```

Putting `$prefix/bin` on `PATH` (via the home-profile activation
pass) gives the operator a transparent launcher. The wrapped binary
sees an FHS-coherent filesystem view inside the namespace.

## Launcher behavior (Linux)

1. Parse the manifest (raw text I/O, no allocator runtime overhead).
2. `unshare(CLONE_NEWUSER | CLONE_NEWNS)`. The user namespace lets us
   `mount(2)` without root; the mount namespace scopes the binds to
   the current process tree.
3. Write `/proc/self/uid_map` + `/proc/self/gid_map` so the
   unprivileged caller appears as root *inside* the namespace --
   `mount(2)` requires CAP_SYS_ADMIN.
4. `mount(MS_REC | MS_PRIVATE)` on `/` so subsequent binds don't
   leak back to the host.
5. For each manifest entry, `mount(MS_BIND, ...)`; for `ro` entries a
   second `mount(MS_REMOUNT | MS_RDONLY)` (Linux ignores `MS_RDONLY`
   on the initial bind).
6. `chdir(cwd)` if requested.
7. `execve(exec_path, argv)`.

## Launcher behavior (Windows)

The launcher parses the manifest and `_execv()`s the target binary
directly. No namespace setup happens because Windows lacks Linux's
user-namespace + bind-mount machinery. Reprobuild's foreign-package
sandbox is Linux-only; the Windows stub exists so cross-platform
tooling (manifest emit + CI smoke) can exercise the parser path.

## Threat model

* The launcher does NOT modify the host filesystem. All bind mounts
  live inside the new mount namespace and disappear when the
  namespace dies (process exit).
* The launcher does NOT preserve setuid bits or file capabilities --
  unprivileged user namespaces drop these per kernel policy. A
  foreign package that needs setuid (e.g. `ping` with `cap_net_raw`)
  will run without those capabilities. This is acceptable for the
  Tier-3 use cases (operator's own tools); production system services
  belong on Tier 1 / Tier 2.
* Signature trust is still Tier 3: the binary is byte-identical to
  the distro's upstream bytes (validated at harvest time via
  `InRelease` GPG), but Reprobuild does not re-verify per-invocation.
  The catalog file itself is consumed on trust at realize time --
  per-catalog signature verification is deferred (see C2 risk #3 in
  the campaign spec).
* The launcher's `--dry-run` lets operators audit the manifest before
  the unshare; combined with `--verbose` it surfaces every bind
  operation.

## Performance

The C3 spec stipulates sub-100ms launcher overhead. Measured on WSL2
Ubuntu 22.04 (kernel 6.18, x86_64):

| metric              | observed |
| ------------------- | -------- |
| p50 wall-clock      | 3 ms     |
| p95 wall-clock      | 4 ms     |

(See `tests/integration/foreign_packages/t_c3_launcher_perf.sh`.)
The overhead is well under budget because the launcher is a single
process with no allocator runtime, no extra `fork()`, and a small
number of `mount(2)` calls.

## Limitations

* **Windows**: the launcher is a no-op stub. Foreign packages can't
  be realized on Windows; this is by design.
* **macOS**: unsupported. macOS lacks Linux's bind-mount machinery;
  the Tier-3 sandbox is Linux-only.
* **Static binaries inside the namespace**: bind-mounting a fresh
  `/lib` over the host's hides the dynamic linker. Tooling that lives
  inside the wrapped binary's environment (e.g. the wrapped binary's
  own `#!/bin/sh` interpreter) must come from the foreign-package
  closure, not the host. Statically linked probes work without any
  bind set.
* **setuid / file capabilities**: stripped (see threat model above).
* **`/etc/resolv.conf` / `/etc/passwd` / `/etc/group`**: not
  bind-mounted by default. Tools that need them must either declare
  the bind in their package's catalog or operate without (DNS via
  `dig +noresolv`, etc.). This is the same trade-off NixOS's
  `buildFHSEnv` makes.
* **GUI applications**: X11 / Wayland sockets, GPU device nodes,
  audio servers are not exposed. Scoped out of the MVP.

## System units: native binding

The launcher above is for an operator's own tools. A **system service** that
runs a foreign package — a Debian daemon on a Debian or Raspberry Pi OS host
whose services Reprobuild manages on top of the distribution — does not use
it. The launcher's unprivileged user
namespace is the problem: a process inside it has no capabilities in the
host's namespace, so `CAP_NET_RAW` (an ICMP prober), root or group access to
USB device nodes (a UPS driver), `DynamicUser=` and `LoadCredential=` all stop
meaning what systemd says they mean. Instead, the unit's own mount namespace
does the work. systemd creates one for any unit with a bind directive, and
the unit gets two lines:

```ini
[Service]
BindReadOnlyPaths=/repro/store/prefixes/apt-closure-<root>/<version>-<hash16>/usr:/usr
InaccessiblePaths=-/etc/ld.so.preload
ExecStart=/usr/bin/prometheus-blackbox-exporter ...
DynamicUser=yes
AmbientCapabilities=CAP_NET_RAW
```

### The closure lock

`repro-harvest-apt --emit-lock` resolves a closure against a signed archive
and writes a `repro-apt-closure-lock v1` file:

```sh
repro-harvest-apt \
  --source 'apt:{prometheus-node-exporter,prometheus-blackbox-exporter}@raspbian/trixie' \
  --archive http://raspbian.raspberrypi.com/raspbian \
  --keyring recipes/catalog/foreign/apt/keys/archives/raspbian-archive-keyring.gpg \
  --arch armhf --components main \
  --emit-lock apt-locks/exporters.lock
```

- `InRelease` is verified against the one keyring given with `--keyring`
  (apt's `Signed-By=`). The verdict is read from gpg's `--status-fd` lines,
  not its exit code: it needs `GOODSIG` and `VALIDSIG` and none of
  `EXPKEYSIG`, `REVKEYSIG`, `EXPSIG`, `BADSIG`, `ERRSIG`, `NO_PUBKEY`,
  `KEYEXPIRED` or `KEYREVOKED`, because gpg 2.4 exits 0 for a good signature
  by an expired key. The signed `Valid-Until` is enforced (a stale but
  correctly signed `InRelease` is refused; snapshot archives carry none),
  each `Packages` index is checked against the SHA-256 the signed `InRelease`
  lists, and each member's SHA-256 and size are taken from that index. The
  lock records all of it. Index downloads are streamed with a size cap.
- The members are the `Depends:`/`Pre-Depends:` closure of the roots plus the
  archive's `Essential: yes` set, which every Debian package may assume
  ([Debian Policy §3.8](https://www.debian.org/doc/debian-policy/ch-binary.html#essential-packages)).
  `--no-essential` leaves that set out. An alternative resolves to a package
  already in the closure when there is one, then to the first that exists. A
  virtual package resolves to its provider with the highest `Priority:`.
- The archive need not have a snapshot service. A Raspbian archive drops
  superseded `.deb`s, so the lock is the pin, and it is committed next to the
  profile that reads it.
- Keyrings for the archives used so far live in
  `recipes/catalog/foreign/apt/keys/archives/`, with their fingerprints and
  sources in that directory's `README.md`.

A profile attaches the lock to a unit:

```nim
systemdSystemUnit(name = "prometheus-blackbox-exporter.service",
  content = blackboxUnit,
  aptClosureLock = staticRead("apt-locks/exporters.lock"))
```

### Realisation

On apply, the privileged driver realises the closure before it writes the
unit (`apt_closure.realiseAptClosure`):

0. The lock's architecture must run on the host (`armhf` on `armv7l` or
   `aarch64`, `amd64` on `x86_64`, ...); any other pairing is a refusal.
1. Each member is streamed into `/var/cache/repro/apt/<sha256>.deb` (a
   directory private to the realising user) with the lock's size as a hard
   cap: a `Content-Length` above it, or one that differs from the lock's
   size, is refused before the body is read, and a body without one is cut
   off at the cap. The file is then checked against the lock's size and
   SHA-256. A mismatch is a refusal; a cached file is checked again every
   time it is used. `https://` archives need a `-d:ssl` build and are
   refused with that message otherwise.
2. Each member's `data.tar.*` is decompressed with the host `xz`, `gzip`
   or `zstd` and unpacked once, by Reprobuild's own tar reader, into
   `/repro/store/prefixes/apt-deb-<name>/<version>-<hash16>/`. The host
   `tar` is not used: what it does with a hostile entry depends on its
   version and on whether it runs as root (GNU tar as root restores setuid
   bits and owners). The reader's policy is fixed:
   - an absolute name or a `..` component is a refusal, not stripped;
   - nothing is written through a symbolic link the archive created, the
     entry itself included;
   - a hard link must name a regular file already extracted from the same
     archive;
   - device nodes, FIFOs, sockets and every other entry type are refused;
   - modes are normalised to `0755` (directories and executables) and
     `0644`: no setuid, setgid, sticky, group- or world-writable bit is
     written, and owners are not restored (files belong to the realising
     user, root on a host).
   No maintainer script runs; `dpkg` and `apt` are never invoked; nothing
   is written to `/usr`. A second pass (`verifyHardenedTree`) refuses the
   prefix if any entry violates the mode or type policy.
3. The closure is a hard-link union of its members at
   `/repro/store/prefixes/apt-closure-<first root>/<version>-<hash16>/`.
   Only `usr/` and `etc/` are kept, and pre-merged-`/usr` top-level
   `bin`/`sbin`/`lib*` directories are folded into `usr/`. Two members that
   ship different bytes at the same path are a refusal, and so is a path
   that would be written through another member's symlink.
4. Both levels are filled in a fresh `0700` temporary sibling, made `0755`
   and marked complete, then published through the store like any other
   prefix: the store seals a `.repro-receipt` into it, renames it into
   place and records it in the store's index.
5. Once a member's prefix exists its cached `.deb` is deleted (the prefix
   supersedes it), so the cache holds only in-flight downloads. Prefixes no
   longer named by any generation belong to the store's garbage collector:
   each generation registers the closure it runs from (the union and its
   members) as a store root, and `repro store gc` collects a prefix no
   root holds once the retention window (never the current or previous
   generation) has passed.

Each `<hash16>` is the store's realization hash for the prefix: for a
member it depends on the realiser version, the package name, version and
architecture and the `.deb`'s SHA-256; for the closure on the realiser
version, the first root's name and version, the architecture and the member
digests. The planner therefore renders the unit offline, and the host
realises exactly the path the unit names. The name and version in the path
keep only `[A-Za-z0-9._-]` and write every other character `_` (so an
epoch's `:`, which separates a `BindReadOnlyPaths=` source from its target,
never appears, and neither do `+` or `~`).

### How the daemon finds its libraries

The unit's `/usr` *is* the closure's `/usr`. The base system's
`/lib → usr/lib`, `/bin → usr/bin` and `/sbin → usr/sbin` links (merged
`/usr`, as on every supported Debian base) resolve into it. A Debian
binary's interpreter (`/lib/ld-linux-armhf.so.3` on armhf) is therefore the
closure's loader, which finds the closure's `libc` and libraries through the
host's `/etc/ld.so.cache` or, on a miss, its built-in multiarch directories.
Both resolve to `/usr/lib/<triplet>/` inside the closure. No `RPATH` is
rewritten and no `LD_LIBRARY_PATH` is set.

`/etc/ld.so.preload` names host libraries. Raspberry Pi OS preloads
`libarmmem-${PLATFORM}.so` from its own archive, and inside the closure view
the loader would print an error on every exec. `InaccessiblePaths=` hides the
file, and the `-` prefix makes the line a no-op on hosts without it.

### What the service sees, and what it does not

| Path | Comes from |
|---|---|
| `/usr` (and `/bin`, `/lib`, `/sbin` through the base's links) | the closure, read-only |
| `/etc`, `/var`, `/run`, `/home`, `/tmp` | the host, governed by the unit's own sandboxing |
| `$CREDENTIALS_DIRECTORY` (`LoadCredential=`) | systemd |
| `/dev` nodes | the host, subject to `DeviceAllow=` / `PrivateDevices=` |

- The package's shipped configuration under `etc/` stays in the prefix for
  reference and is never bound. The profile writes the service's `/etc`
  files itself, for example with `fsSystemFile`.
- Host NSS modules are not in the closure. `files` is part of glibc. A
  service that resolves a `DynamicUser=` name through `nss-systemd` needs
  `libnss-systemd` among its roots.
- A unit takes at most one closure. Name every daemon of a unit as a root of
  that unit's closure.
- The renderer refuses a unit with no `[Service]` section; a unit whose
  command lines name `reprobuild-sandbox-launcher`; a unit that sets
  `RootDirectory=` or `RootImage=`; an empty `BindPaths=`,
  `BindReadOnlyPaths=` or `InaccessiblePaths=` (an empty assignment resets
  the list systemd has built, dropping the closure's own lines); and any
  bind, `TemporaryFileSystem=` or `InaccessiblePaths=` whose destination is
  `/usr` or under it. Comment lines (`#`, `;`) are not read. The broker
  applies the same refusals to the rendered unit it receives, and requires
  the closure's bind line exactly once, before it realises the lock.
