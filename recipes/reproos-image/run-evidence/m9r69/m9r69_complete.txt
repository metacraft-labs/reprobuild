Phase A — seatd binary + segfault audit (M9.R.69.1)
----------------------------------------------------
Mounted M9.R.68 reproos-installed.qcow2 read-only + inspected seatd
ELF (readelf -d, INTERP, .rodata /nix/store leaks, DT_NEEDED).
Reproduced the "segfault at 2 ip 0x2 error 14" crash inside a
chroot copy of the image rootfs.  Signature = indirect-call-through-
NULL, RIP=0x2, Code: "Unable to access opcode bytes at 0xffffffffffffffd8".

Structural findings:
  * INTERP = /repro/store/xx7cm72*/lib/ld-linux-x86-64.so.2
    (glibc 2.40 hash xx7cm72...).
  * DT_NEEDED = libc.so.6 only (no libudev, no libsystemd — seatd
    daemon is minimal).
  * DT_RUNPATH = 11 entries (meson + 6xsystemd + clingo + gcc-lib +
    3x$ORIGIN) — NONE containing glibc's lib dir.
  * Symbol-version demand = GLIBC_2.2.5 through GLIBC_2.34 — BOTH
    the Nix 2.40 AND the Debian 2.41 libc.so.6 satisfy this.

Chroot LD_LIBRARY_PATH direct-swap test proved the ip=0x2 crash is
an ld-linux + libc.so.6 VERSION MISMATCH:
  LD_LIBRARY_PATH=/lib/x86_64-linux-gnu (Debian 2.41)         crash
  LD_LIBRARY_PATH=/repro/store/xx7cm72*/lib (Nix 2.40)        seatd -h prints OK

Evidence: m9r69_phaseA_seatd_analysis.txt.


Phase B — root cause classification (M9.R.69.2)
-----------------------------------------------
Applied the task-brief taxonomy alpha..epsilon:

  alpha (dlopen backend zero-init):  FALSIFIED — crash reproduces on
                                     "seatd -h" before any backend
                                     registration.
  beta (unresolved GOT symbol):      FALSIFIED — symbol demand satisfied
                                     by both glibcs.
  gamma (TLS init / static-TLS):     FALSIFIED — SAME-hash libc test
                                     succeeds.
  delta (libudev vtable):            FALSIFIED — seatd daemon doesn't
                                     link libudev; DT_NEEDED only libc.
  epsilon (recipe bug):              CONFIRMED — meson doesn't record
                                     glibc's lib dir in RPATH because
                                     it treats glibc as an implicit
                                     toolchain input.

Same bug M9.R.58.3 characterised.  Fix was applied on the qcow2 via
_m9r58_swap.sh's "patchelf --set-rpath" (prepend the glibc lib dir
extracted from the interpreter path) but NEVER LANDED into the
reproducible-build path (repro.nim or build-reproos-image.sh).
M9.R.68's clean rebuild regressed the fix.

Evidence: m9r69_phaseB_root_cause.txt.


Phase C — the fix (M9.R.69.3)
------------------------------
Chose scripts/build-reproos-image.sh Phase 10.9 as the fix site (the
existing seatd-service installation phase already gated on libseat).
Rejected the DSL-postInstall alternative (bigger scope) + the
meson-auto-rpath alternative (would need per-recipe re-application).

The Phase 10.9 sub-shell now:
  1. Locates patchelf on PATH (fails-loud with a M9.R.58.3-referenced
     warning if absent).
  2. For each of seatd, seatd-launch, libseat.so.1 under
     $MNT_DIR/opt/repro/.../install/usr/{bin,lib}/:
     * Extract the glibc lib dir from patchelf --print-interpreter
       (strip the trailing '/ld-linux-x86-64.so.2').
     * For libseat.so.1 (no INTERP), reuse the glibc lib dir
       computed from seatd's interpreter.
     * If DT_RUNPATH doesn't already contain the glibc lib dir:
       prepend it via patchelf --set-rpath.
  3. Idempotent — case-glob against ":$glibc_libdir:" on the
     existing colon-list.

Fires against the on-disk copies in the mounted image root — the
host install-mirror is intentionally NOT mutated.  Future recipe
rebuilds still emit an un-patched binary; Phase 10.9 re-applies the
patch each image build.

Behind the seatd fix: NEW residual (retroactive M9.R.59)
--------------------------------------------------------

This is the M9.R.58/59 residual class.  The shipped
libwlroots-0.19.so was built 2026-07-02 19:12, BEFORE M9.R.59's
hwdata + libdisplay-info recipes landed hwdata/libdisplay-info as
buildDeps into wlroots' repro.nim.  Empirical proof — the compiled
libwlroots.so has ONLY libinput + wayland + headless backends baked
in; no "backend/drm/*.c" strings, no "drm_backend_create" symbol.

M9.R.59 close-out marked this as blocked at the "monitor-depfile
infrastructure" layer with the note "the recipe-level publish is
correct; the next milestone that fixes the auto-recurse path can
consume both from-source recipes verbatim."  M9.R.60-68 did not
rebuild wlroots.  M9.R.68 clean-rebuild reused the stale install-
mirror.

Attempted mid-milestone rebuild: reproduced the M9.R.59 blocker at
a NEW level.  hwdata's recipe declares a "files hwdataFiles"
artifact but the from-source-custom mirror-emit action wipes and
re-populates the install-mirror with ONLY the sanity marker
(pnp.ids -> hwdataFiles), NOT the full "usr/share/hwdata/*.ids"
tree.  Manually populating the hwdata install-mirror via
_m9r59_build_hwdata.sh then triggering wlroots build via
"repro build --tool-provisioning=from-source recipes/packages/source/wlroots"
also fails at mesonbin-setup (no log surfaced — a separate build-
engine-cache write gap).

Closing the wlroots DRM residual therefore requires a proper
M9.R.60-class fix, not a mid-M9.R.69 hack.  Documented as the
M9.R.69 residual for M9.R.70.
