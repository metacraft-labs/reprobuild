Objective
---------
reprobuild-specs Filesystem-Policy-And-Observed-Inputs.md §"Double
Writes" (R7, lines 246-262) + §"Source Rewrites" (R6, lines 264-278)
mandate that (a) two producers writing the same output are errors,
and (b) actions writing to nominally-read-only source paths are
errors. The M9.R.72 Phase A summary flagged both as "Gap VI (low
impact for M9.R.60-70 but spec-mandated): source-rewrite and
double-write enforcement (R6/R7) is missing." M9.R.74 landed the
foundational ActionCwdKind + resolveCanonicalExecRoot; this milestone
lands the R6 + R7 enforcement layers on top.

Phase A summary — spec reading + gap enumeration
-------------------------------------------------
Filesystem-Policy-And-Observed-Inputs.md §"Double Writes" (R7,
lines 246-262):

    A double write occurs when more than one producer writes the
    same output.
    ...
    The default should be the strictest safe behavior:
    - double writes are errors

Filesystem-Policy-And-Observed-Inputs.md §"Source Rewrites" (R6,
lines 264-278):

    A source rewrite occurs when an action mutates a source or
    other nominally read-only file.
    ...
    The default should be:
    - source rewrites are errors

Current-implementation grade at Phase A:

  * R7 partially implemented — ``validateGraph`` at
    libs/repro_build_engine/src/repro_build_engine.nim:986-1002
    rejects two actions declaring the same string in ``outputs``, but
    conventions declare only stamp files there (unique per action by
    design), so the check misses the real hazard (two configure /
    install actions racing for the same buildDir / DESTDIR).

  * R6 not implemented — monitor evidence records ``mrFileWrite`` per
    path but no engine code classifies them against a "source root"
    allowlist.

Phase C summary — R6 source-write reject via post-hoc monitor check
--------------------------------------------------------------------
libs/repro_build_engine/src/repro_build_engine.nim
  + detectSourceWrites* — exported helper. Given readOnlyRoots +
    monitorWrites, returns every (write, root) pair where the write
    landed at or under a read-only root.
  + collectEvidence extends the monitor-fold pass with an R6 check
    after ``foldMonitorDepFileEvidence`` populates monitorWrites;
    any offender flips ``result.publishable`` to false with a
    structured "source-write attempt (R6): ..." diagnostic.
  + publishable = false is the same escalation channel M9.R.72.3's
    monitor-loss ladder uses; the scheduler's post-execution check
    at line 4691 flips asSucceeded → asFailed when
    evidence.publishable is false, so source-write attempts land as
    hard action failures with the full diagnostic in stderr.

Enforcement Shape chosen: Shape B (post-hoc monitor check,
cross-platform). Shape A (Linux bwrap sandbox) is architecturally
correct + immediate for Linux but requires wiring bwrap into the
engine's spawn wrapper — deferred to a follow-up milestone.

Fetch actions leave readOnlyRoots empty per R6's "action explicitly
owns the target location" carve-out; legacy actions predate the
field entirely so both cases no-op byte-for-byte.

Phase C.1 summary — R7 dep-chain relaxation
--------------------------------------------
The Phase B R7 pass fired on ANY two actions declaring overlapping
write roots. But the canonical from-source pattern is configure →
compile → install all declaring the same buildDir — these are
SEQUENTIAL, not double writes.

Refined semantic: R7 targets CONCURRENT double writes. Two actions
whose declaredOutputs overlap are only rejected when NEITHER
transitively depends on the other. Uses a bounded DFS reachability
probe on the byId table.

Regression added 2 new cases to test_m9r75_double_write_reject.nim:
  * sequential actions (direct dep chain) sharing a write root are
    allowed;
  * transitive dep chain (C deps B deps A, C+A shared root) allowed.

All 9 R7 tests now pass.

Deferred to follow-up milestones
---------------------------------

1. **meson_package / autotools_package / cmake_package thread-through.**
   These three high-level constructors emit configure / compile /
   install edges through typed-tool call sites (``meson(...)`` /
   ``make(...)`` / ``cmake(...)``) rather than direct ``buildAction()``.
   Threading ``declaredOutputs`` + ``readOnlyRoots`` requires
   extending the typed-tool call-site emitter OR the fragment
   assembler that turns each call site into a ``BuildActionDef``.
   Not one-milestone work — this milestone lands the MECHANISM;
   the follow-up lifts the conventions to populate the new fields.

2. **Shape A (bwrap sandbox) on Linux.** Phase C landed Shape B
   (post-hoc monitor check) as the immediate cross-platform
   enforcement. Shape A would wrap each action's spawn in
   ``bwrap --ro-bind $ro $ro --bind $rw $rw ...`` so writes to the
   source tree fail hard with EROFS INSIDE the action, not just at
   the post-hoc evidence-fold stage. Requires wiring bwrap into
   the engine's spawn wrapper (``startBypassRunQuotaProcess`` +
   ``startRunQuotaProcess``) with the tool catalog for Linux hosts;
   Windows keeps Shape B as the sole enforcement.

3. **``outputs`` vs ``declaredOutputs`` naming disambiguation.**
   The engine's legacy ``BuildAction.outputs`` field represents the
   per-action stamp / artefact set; the M9.R.75
   ``BuildAction.declaredOutputs`` represents the write ROOT for R7
   grading. Two orthogonal concepts with confusingly similar names.
   A follow-up doc pass could rename to ``declaredArtifacts`` /
   ``writeRoots`` for clarity; codec would need a v23 rename.

4. **Same-content double-write hatch.** Spec R7 line 260 allows
   "same-content double writes may be acceptable in carefully
   controlled cases" as a non-default policy. The M9.R.75 code
   implements only the strict default; a follow-up milestone could
   thread a per-action ``sameContentDoubleWriteOk = false`` slot
   through the payload codec for the tightly-controlled cases the
   spec permits.
