Phase D — boot smoke + fix iteration (M9.R.78.4 v1..v4)
-------------------------------------------------------
Each iteration ran the same shape:
  (a) rebuild reproos-image (~22 min per pass — no cache hits due to
      wrapper edits) + boot smoke (300s)
  (b) mount qcow2 snapshot layer via qemu-nbd
  (c) inspect /var/log/m9r71_sway.log to see the next-layer trip
  (d) update /usr/local/bin/repro-sway-diag wrapper
  (e) commit + push + goto (a)

Iteration v1 (initial Mesa 24.0.9 boot):
  Same error as M9.R.71 v4:
    did not find extension DRI_IMAGE_DRIVER version 1
    failed to bind extensions
    [ERROR] [wlr] [render/egl.c:595] Failed to create GBM device
  Root cause traced via Mesa 24.0.9 source:
    - The wrapper's ``export MESA_LOADER_DRIVER_OVERRIDE=swrast``
      short-circuits gbm's software-fallback: it forces
      ``dri_screen_create_for_driver(dri, "swrast")`` with a non-NULL
      driver_name -> gbm applies the STRONGER
      ``gbm_dri_device_extensions`` matcher (requires DRI_IMAGE_DRIVER)
      but the loaded pure-swrast driver's extension list
      ``galliumsw_driver_extensions`` does NOT publish DRI_IMAGE_DRIVER.

Iteration v2 (M9.R.78.4a: drop override):
  DRI_IMAGE_DRIVER error CLOSED. Next-layer trip:
    pci id for fd 12: 1234:1111, driver (null)
    MESA-LOADER: failed to open bochs-drm:
      /opt/.../mesa/.repro/output/install/usr/lib64/dri/bochs-drm_dri.so:
      cannot open shared object file
  Root cause: Mesa's DRI loader identifies QEMU's virtual GPU as
  ``1234:1111`` (Bochs graphics), sets driver_name="bochs-drm", and
  dlopens ``bochs-drm_dri.so`` — but our v1 minimal Mesa builds only
  ``gallium-drivers=swrast``. No bochs-drm DRI backend exists.

Iteration v3 (M9.R.78.4b: MESA_LOADER_DRIVER_OVERRIDE=kms_swrast):
  MESA-LOADER "failed to open bochs-drm" line CLOSED. Next-layer trip:
    [ERROR] [wlr] [render/egl.c:595] Failed to create GBM device
  (no explicit MESA-LOADER diagnostic — override is honoured but
  gbm_create_device still returns NULL from a deeper failure).

Iteration v4 (M9.R.78.4c: GBM_ALWAYS_SOFTWARE=1):
  Reading Mesa 24.0.9's ``gbm/backends/dri/gbm_dri.c:dri_device_create``,
  the top-level branch is:

    force_sw = debug_get_bool_option("GBM_ALWAYS_SOFTWARE", false);
    if (!force_sw) {
       ret = dri_screen_create(dri);      // pci-id -> "bochs-drm"
       if (ret)
          ret = dri_screen_create_sw(dri);
    } else {
       ret = dri_screen_create_sw(dri);
    }

  Setting GBM_ALWAYS_SOFTWARE=1 forces force_sw=true, bypassing the
  hardware-driver path entirely.
  Result: [ERROR] [wlr] [render/egl.c:595] Failed to create GBM device
          STILL FIRES. gbm's dri_screen_create_sw path (loading
          kms_swrast_dri.so) also fails silently at
          ``dri_swrast_kms_init_screen`` -> ``pipe_loader_sw_probe_kms``
          -> ``pipe_loader_create_screen`` — which is the softpipe/
          llvmpipe fallback probe. Our v1 minimal Mesa builds without
          LLVM (``llvm=disabled``) and without ``draw`` LLVM support
          (``DRAW_LLVM_AVAILABLE=0``), so the software pipeline
          probe may not construct a valid pscreen against the
          bochs-drm KMS fd.


sddm autologin -> sway path VERIFIED via strace
-----------------------------------------------
Full detail: m9r78_v1_sddm-strace.log + m9r78_v4_sddm-strace.log.

sddm-helper spawned sway 4 times (session ids 2, 3, 4, ...) via
the wrapper -> /usr/share/sddm/scripts/wayland-session ->
``/bin/bash --login -c 'exec "$@"' - /usr/bin/sway``. Each attempt:
  1. sddm-helper opens /var/log/m9r71_sway.log (durable capture).
  2. execve /usr/local/bin/repro-sway-diag /usr/bin/sway succeeds.
  3. Wrapper preamble writes env-vars + drm state.
  4. sway execve succeeds.
  5. sway loads /etc/sway/config, prints [ERROR] [wlr] Failed to
     create GBM device.
  6. sway CONTINUES past the EGL failure — creates
     $XDG_RUNTIME_DIR/wayland-1 socket + sway-ipc.1000.<pid>.sock.
  7. sway attempts to execve /usr/bin/swaybg (background wallpaper)
     and /usr/bin/swaybar (status bar); both ENOENT (not shipped in
     the from-source install-mirror).
  8. sddm-helper's 30s watchdog fires SIGKILL because the sway
     session doesn't hand-shake with sddm's session-alive protocol.

Sway IS running the compositor loop in headless-backend fallback
mode — same behavior class as M9.R.71 v4, but now via a genuinely
Mesa-24.0.9-provided software pipeline (not the 23.3.6 pipeline).

Honest residual
---------------
M9.R.78 chartered scope: PARTIALLY CLOSED at the Mesa recipe +
wlroots drm-backend layer. The DRI_IMAGE_DRIVER v1 gap from the
M9.R.71 close-out is functionally CLOSED (wlroots' meson probe
consumes it correctly + Mesa 24.0.9 publishes it). BUT the
compositor still can't create a GBM device at runtime against
QEMU's bochs-drm KMS fd because the LLVM-less software pipeline
can't construct a working pipe_screen.

New residual (M9.R.79+ material):

  (vii) Mesa software-pipeline can't render on bochs-drm — Mesa
        24.0.9's ``dri_swrast_kms_init_screen`` calls
        ``pipe_loader_sw_probe_kms(&screen->dev, screen->fd)`` which
        expects a working softpipe/llvmpipe. Our v1 minimal Mesa
        ships ``llvm=disabled`` -> ``DRAW_LLVM_AVAILABLE=0`` -> the
        LLVM-less softpipe path may not initialise a pscreen against
        the KMS fd. Fix shapes to explore:
          (a) Add ``llvm=enabled`` (pulls LLVM into the reproos-image
              closure — several GB of extra .so).
          (b) Add ``gallium-drivers=swrast,virgl`` (virgl is the
              virtio-gpu paravirt renderer; better fit for QEMU
              than bochs-drm).
          (c) Switch QEMU's GPU model from ``-vga std`` (bochs-drm)
              to ``-device virtio-vga-gl`` in the boot smoke script
              (host-side workaround; the recipe stays as-is).
          (d) Investigate the ``gallium-drivers=softpipe`` explicit
              enum (24.0's ``swrast`` alias may map to a different
              backend than 23.3's).

  (i) monitor depfile is incomplete:      unchanged (persists from
                                          M9.R.68 wrapper level; the
                                          qcow2 build IS complete +
                                          bootable regardless).
