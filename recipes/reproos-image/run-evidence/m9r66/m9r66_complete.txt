Phase A — SYS_gettid (M9.R.66.1)
--------------------------------
M9.R.65 residual class (1): `libc raw syscall unsupported nr=186`
× 2 on every mesonbin-setup, tripping mcIncomplete for meson's Python
runtime that calls `syscall(SYS_gettid)` per thread.

Fix: added `LinuxSysGettid = 186` to the raw-syscall constant table
in `io-mon/src/io_mon/shim/linux_preload.nim` and a new case in
`classifyRawFileSyscall` that returns `true` (supported) without
emitting any observation. SYS_gettid returns the calling thread's
tid — no I/O, no filesystem interaction, no observation to record.

Regression pin: `tests/linux/test_io_mon_linux_stdio_ipc.nim`'s new
"raw libc SYS_gettid is treated as supported (no event-loss)" test
asserts mcComplete + no unsupported-syscall event-loss for a probe
that issues `syscall(SYS_gettid)`. The pre-existing "unsupported raw
libc syscall still fails closed" test (uses SYS_getpid=39) still
guards the fail-closed default for genuinely unknown numbers.


Phase B — mesonbin-setup subtree characterization (M9.R.66.2 evidence)
----------------------------------------------------------------------
See `m9r66_phaseB_subtree.txt` + `m9r66_phaseB_mesonbin_records.txt`.
Characterization identified the second class as T0 signal (b) firing
because pid=3591461 emitted 4 `mrProcessExec` records against only
2 `mrProcessStart` records for the same pid:

    #1263 process-exec path=/nix/store/…-gcc-14.3.0/bin/gcc
    #1264 process-exec path=/nix/store/…-meson-1.9.1/bin/gcc
    #1265 process-exec path=/nix/store/…-ninja-1.13.1/bin/gcc
    #1266 process-exec path=/nix/store/…-gcc-wrapper-14.3.0/bin/gcc

Four candidate paths for the SAME pid. Root cause: Python's
`_posixsubprocess.fork_exec` on Linux uses vfork+execvp; glibc's
`execvp` implementation calls `execve()` internally per PATH
candidate, and each of those internal execve calls hit the shim's
LD_PRELOAD `execve` interposer OUTSIDE the manual CT_CALL_HOOK
bracket that M9.R.65.2's `dispatch_execvp` fires. Each failed
candidate emitted one spurious `mrProcessExec` before the successful
transition.


Phase C — the two-part fix (M9.R.66.2 + M9.R.66.5)
---------------------------------------------------
Part 1 — M9.R.66.2 shim-side bracket
    `dispatch_execvp` / `_execvpe` / `_fexecve` now bracket the
    `real_exec` call inside `stackable_linux_preload_enter_hook()` /
    `_exit_hook()`. This suppresses PATH-loop re-entry into our
    execve interposer for callers that DO go through libc's
    `execvp` symbol (bash's `exec` builtin, etc.). Regression pin
    `test_io_mon_linux_stdio_ipc.nim` verifies the direct-execvp case.

Part 2 — M9.R.66.5 writer-side relaxation
    Python's fork_exec DOES NOT go through libc's `execvp` — it
    inlines its own PATH search in C, calling `execve()` per
    candidate directly. Our LD_PRELOAD `execve` interposer catches
    each of those. No shim-side pre-check attempt survived (see
    Phase D honest residual on M9.R.66.3's cc1 regression).

    Fix in `io-mon/src/io_mon/writer.nim`'s
    `unmonitoredSubtreeLossCount`: T0 signal (b)'s
    `execCount(pid) >= startCount(pid)` invariant now applies ONLY
    to pids with a matching `mrProcessSpawn` record (the root
    synthetic counts). Unanchored pids — including Python-vforked
    children — are exempt from signal (b). Signals (a) and (c)
    (un-injected spawn from monitored parent + IPC-connect to
    out-of-tree peer) remain fully active.

    Rationale: for un-injectable-exec detection, an unanchored pid
    already lacks the initial-shim-load `mrProcessStart` invariant
    (either vfork bypassed our fork hook, or the parent's spawn
    mechanism was outside our hooks). Without that invariant we
    cannot distinguish "un-injectable exec" from "PATH-search
    false-positive execs" without a shim-side pre-check that
    breaks gcc-14.3.0's cc1 (M9.R.66.3 → M9.R.66.4 revert).

    Regression pin: `tests/portable/test_io_mon_t0_completeness.nim`
    — classical un-injectable case still trips iff the root-spawn
    synthetic `spawn(0, pid)` is present (which mergeFragments
    always injects for the launcher-expected root); new tests
    lock in the unanchored-pid exemption.

Both M9.R.65 residual classes are CLOSED on the depfile.

Recipe-level status: the pixman meson `sanitycheckc.c` compile
fails with an internal compiler error in gcc-14.3.0's `cc1`
(init_emit_regs segfault). Phase D bisection identified this as
INDEPENDENT of any M9.R.66 change:

  1. gcc-14.3.0 compiles cleanly with NO LD_PRELOAD.
  2. gcc-14.3.0 crashes under our shim when the shim is built via
     reprobuild's `nix develop` (config.nims `undef nixbuild`).
  3. gcc-14.3.0 runs cleanly under the SAME shim source when
     built from io-mon's directory (default `nim.cfg` keeps
     `nixbuild` defined).

The differentiator is reprobuild's `config.nims` line 30-33
`switch("undef", "nixbuild")` which reprobuild uses to avoid Nim's
stdlib dynlib pragma baking absolute /nix/store paths into
`.rodata`. Undefining `nixbuild` produces a shim binary that
crashes gcc-14.3.0's cc1 at startup. Byte-identical shims copied
into `/opt/repro/reprobuild/build/lib/` vs `/tmp/` also behave
differently (path-dependent) — a lower-level ld.so or dlopen
interaction we did not further characterize.

This regression is PRE-EXISTING (visible on M9.R.65's shim too when
built via `nix develop`); M9.R.65's pixman Phase E used a
different build path that happened to avoid it. It is orthogonal
to the io-mon-side chartered work and belongs to a follow-up
milestone. Suggested fix path: force `-d:nixbuild` when
`build_shim.sh` runs under reprobuild's dev shell, or split the
shim into a nixbuild-defined package that reproos-relocation
patches via patchelf like the rest of reprobuild's binaries.

Signal (b) coverage note: unanchored pids (Python fork_exec
children) no longer trip signal (b) even for a genuinely
un-injectable exec. Coverage is preserved for anchored pids
(signal (b) unchanged) and for spawn-from-monitored-parent chains
(signal (a) unchanged) and for IPC-connect breakaways
(signal (c) unchanged). The residual gap is narrow: an
UNANCHORED pid that legitimately execs into a hardened image.
In practice this pattern requires vfork+SETEXEC or similar,
which is rare in build workloads.
