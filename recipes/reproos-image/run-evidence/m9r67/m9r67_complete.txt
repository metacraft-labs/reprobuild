Phase C — root cause: `shouldPatchInlineSyscallMapping` bug
-----------------------------------------------------------
`io_mon/hooks/linux_preload_runtime.nim :: shouldPatchInlineSyscallMapping`
before the fix ran the executable-mapping short-circuit BEFORE the
`isSystemRuntimeMappingPath` / `isMonitorShimMappingPath` exclusions:

    let normalized = normalizeMappingPath(mapping.path)
    if normalized == executablePath:
      return true                        ← patched cc1 anyway
    if isMonitorShimMappingPath(normalized) or
       isSystemRuntimeMappingPath(normalized):
      return false

For a monitored subtree with a `/nix/store/…-gcc-14.3.0/…/cc1`
top-of-tree exec, the early-return patched cc1 despite the docstring
saying `/nix/store/` is toolchain runtime that must NOT be patched.
`looksLikeLinuxX8664Syscall`'s conservative `0F 05 XX` byte-level
predicate false-positived on a byte sequence inside a legit non-syscall
cc1 instruction; INT3 replacement mid-instruction crashed cc1 with
SEGV_MAPERR si_addr=0x3a0 at `init_emit_regs()`.

Filename-dependence: when the shim's own mapping is at
`librepro_monitor_shim.so`, `isMonitorShimMappingPath` excludes it
correctly. When renamed (`shim.so`), the shim's own mapping falls
through to `endsWith(".so") -> true` and its own text is patched too —
which apparently perturbs the same code path enough that cc1's crash
does not trigger (likely because patching the shim's own text under
its own execution context aborts the patch scan via
`installInt3SyscallPatchTransaction` returning an error before it ever
reaches cc1's mapping). Both configurations are wrong; only
`librepro_monitor_shim.so` deterministically manifests the crash.

Phase D — fix (M9.R.67.1 + M9.R.67.2)
-------------------------------------
M9.R.67.1 (io-mon commit faa6cbf) — swap the two clauses in
`shouldPatchInlineSyscallMapping` so the system-runtime / monitor-shim
exclusions run BEFORE the executable short-circuit. A monitored
toolchain exec under `/nix/store/`, `/lib/`, `/lib64/`, `/usr/lib/`, or
`/usr/lib64/` is now correctly SKIPPED. A user-app exec under `/tmp/`,
`/home/`, `/opt/` (outside those prefixes) is still patched, so the
M9.R.63.2 inline-asm `exit_group` regression pin remains covered.

Regression: `io-mon/tests/linux/test_io_mon_inline_patch_predicate.nim`
exercises 8 predicate branches (both exclusion cases + executable
exemption + user-app patching + writable/anon/shared skipping).

M9.R.67.2 (io-mon commit 449d9ce) — after the shim stopped crashing
cc1, the next-layer residual surfaced: 47× `libc raw syscall
unsupported nr=425` / `nr=426` event-loss on the pixman `mesonbin-setup`
depfile. Python 3.13's stdlib uses io_uring internally under recent
kernels (WSL2 5.19+ / native Linux) for its buffering / signal-fd wake
paths.

Classify `io_uring_setup` (425) and `io_uring_enter` (426) as supported
without recording, mirroring M9.R.66.1's SYS_gettid treatment. Python's
own io_uring usage in the stdlib does NOT perform file-open / file-read
/ file-write against sources or outputs — those still route through
open(2) / read(2) / write(2) libc symbols the shim already hooks.

Regression: new "raw libc io_uring_setup probe (failing) is supported
(no event-loss)" test in
`io-mon/tests/linux/test_io_mon_linux_stdio_ipc.nim`.

Residual, honestly
------------------
STRICTLY SMALLER than M9.R.66's residual on M9.R.67's chartered scope:

  * M9.R.66 residual: cc1 crashes under the LD_PRELOAD shim, blocking
    every meson-driven from-source recipe compile.

  * M9.R.67 residual (shim scope, closed): cc1 runs cleanly under the
    shim. Pixman succeeds end-to-end. All M9.R.57-59 wlroots-family
    meson-setup actions run their cc1 compiles without SIGSEGV.

  * M9.R.67 residuals (OUT of shim scope, deferred):
    - sway's mesonbin-compile blocks on missing libdrm + libinput
      from-source recipes (recipe cascade coverage gap; not a shim
      issue). Would have blocked the same way even without M9.R.67.
    - reproos-image full-rebuild blocks at the first tool-provisioning
      sub-build (bash Autotools ./configure) with 12 T0 unmonitored-
      subtree signal-(a) event-losses across 6385 processes / 1.6M
      records. This is a distinct T0-completeness residual (M9.R.66.5's
      unanchored-pid exemption covers signal-(b) but not signal-(a));
      follow-up milestone owns.

  * Documented io_uring gap: an application that DELIBERATELY submits
    real I/O SQEs through io_uring is unmonitored by this backend. A
    future `io_uring_enter` SQE-decoder extension can close it. Python's
    stdlib use of io_uring for internal buffering / signal-fd wake ups
    does NOT open this gap because it never routes file I/O through the
    ring — real file I/O still traverses open(2) / read(2) / write(2).
