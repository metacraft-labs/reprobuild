M9.R.61 Phase B: re-verification of the M9.R.60.D residual on the
hardened io-mon tip (451eb2d)
=================================================================

Objective
---------
Repeat M9.R.60 Phase D's pixman `__repro_provider_compile` rebuild
against the io-mon pin bumped in M9.R.61.1 (`8b05657c` → `451eb2d`,
71-commit delta whose tip carries the two direct-exit + pre-exec flush
commits) and determine whether the "monitor depfile is incomplete"
gate is closed by the upstream hardening alone.

Netting `read-tail-pending` vs `read-tail-committed` markers in

markers across 182 distinct child pids.


Why the upstream flush commits don't cover this class
------------------------------------------------------
The two direct-exit + pre-exec flush commits (`f428b9b`, `451eb2d`)
add a new `ExitContext` + `ct_exit_hook` registration and a
`ct_linux_preload_real_exit` raw-syscall trampoline, plus flush the
fragment on `_exit` / `_Exit` / execve. The shim's own
`repro_hook_exit` calls `repro_monitor_shim_shutdown` →
`closeFragmentSlot` (writes the committed marker, closes fd);
`repro_hook_execve` calls `repro_monitor_shim_flush` (same closure
minus the shutdown-marker recording).

The class the two commits DO cover is: an app that reaches libc's
`_exit` / `_Exit` / `execve`. The class STILL escaping in the pixman
compile is 182 subprocesses that:

  * did emit `linux-preload-hooks` process-start (so the shim WAS
    loaded); and
  * did emit `read-tail-pending` (so their per-thread batch went
    dirty at least once); but
  * emitted NO matching `read-tail-committed` before their fragment
    handle stopped being appended to.

Inspection of the exec chain for a representative escaping pid
(3053571): `clang-wrapper cc` → `bash-interactive sh` → `/bin/sh`,
then three `fork` spawns of pipeline pids. Every escape belongs to
the same shape — a bash-wrapped clang subshell where the parent
bash forks a pipeline child and the child dies in a way that DOES
reach `_exit` (proved by the fragment file being closed cleanly and
no corrupt-fragment record firing) but leaves the sentinel dirty.

The most-likely root-cause candidates ordered by probability, all
requiring a fix in io-mon:

  Candidate 1 — post-fork sentinel-state leak. `repro_hook_fork`
    on the child branch calls `discardFragmentSlotAfterFork`, which
    resets `fragmentSlot.readingSentinelActive` to `false` inside
    the child. HOWEVER the PARENT's on-disk `read-tail-pending`
    marker (already emitted with the parent's osPid+threadId) is
    still on the parent's fragment; if the parent then dies via a
    path the exit-hook does not observe, the marker remains
    unmatched. `discardFragmentSlotAfterFork` does not itself
    emit `read-tail-committed` before closing the inherited fd
    — the assumption being that the parent will flush its own copy
    of the batch later. If the parent instead exits via a raw
    exit_group syscall (glibc's pthread_exit → _exit fast path
    inside the last thread), the un-flushed pending remains.

  Candidate 2 — race between execve's `repro_monitor_shim_flush`
    and the exec kernel-transition. `execve` returns success by
    NOT returning at all; the hook writes the committed marker,
    calls flushFile, closes the fd, then calls the real execve.
    If the flushFile buffer or the fd close were to be reordered
    against the kernel's atomic-exec transition, the write could
    be lost.

  Candidate 3 — CT_BYPASS gating. The fork/execve hooks both bail
    to `callNext(ctx)` when `shouldBypass()` is set. The bypass
    flag is TLS-scoped and inherited across fork copy-on-write;
    a child that inherits `disabled > 0` never emits process-start
    itself but the parent's on-disk pending remains.

Any of these three could account for 182 of ~838 subprocess exits
on this workload. The next milestone (M9.R.61.3) needs to bisect
against a minimum-viable reproducer, starting with Candidate 1
because it is the only shape whose fix is orthogonal to the
existing exit/exec hardening — the other two are supersets of
what M9.R.60.D already characterised.
