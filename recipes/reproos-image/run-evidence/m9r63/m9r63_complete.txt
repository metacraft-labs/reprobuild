FINDING: M-FW-3C accepted 2026-06-30 landed the FULL INT3 raw-syscall
callsite substrate in stackable_hooks/platform/linux_raw_syscalls:

  installInt3SyscallPatchTransaction — patch 0f 05 -> INT3
  installLinuxSigtrapHandler         — SIGTRAP install + chain substrate
  captureLinuxX8664SyscallRegisters  — ucontext -> (nr, args)
  replayLinuxX8664SyscallRegisters   — issue the real syscall
  writeLinuxX8664SyscallResult       — result back to ucontext
  visitLinuxExecutableMappingSyscalls — per-mapping visitor
  enumerateLinuxExecutableMappings   — /proc/self/maps enumerator

FINDING: io-mon already CONSUMES this substrate at
src/io_mon/hooks/linux_preload_runtime.nim (installInlineSyscallPatches
+ ct_linux_inline_syscall_sigtrap_handler). Two gaps:

  Gap 1 (WIRING, Fix Part A): the SIGTRAP handler unconditionally
    called stackable_linux_replay_syscall_regs even when the trapped
    syscall was SYS_exit_group / SYS_exit — both of which never
    return. So the fragment slot was never flushed, and
    mergeFragments injected a synthetic kill-before-flush event-loss.

  Gap 2 (POLICY, Fix Part B, defense-in-depth): libc's `_exit` /
    `_Exit` internal alias `__GI__exit` sits inside libc.so.6, which
    isSystemRuntimeMappingPath excludes broadly for correct reasons.
    LD_PRELOAD cannot interpose the internal binding, so `return 0`
    from `main()` reaches an unhooked inline `syscall #exit_group`.

HONEST NEGATIVE result: the pixman escape shape is NEITHER of

  (a) inline `syscall #exit_group` in a scanned mapping [C-probe]
  (b) libc `_exit` / `_Exit` internal-alias inline `syscall`

The M9.R.62.4 attribution ("INLINE-ASSEMBLY raw SYS_exit_group /
SYS_exit issued from user code") was INCOMPLETE. The actual pixman
escape must be through a DIFFERENT path, still consistent with the
diagnostic evidence at M9.R.62.3b:

  * shim loaded (constructor + recordProcessStart)
  * emitted a captured-dependency record (kind=4 = mrFileOpen)
  * died without entering fork / execve / exit hooks
  * died without the libc destructor firing
  * died without any of the 10 default-terminating signals
  * died without calling libc syscall(3) for SYS_exit_group
  * died without an inline `syscall #exit_group` at a scanned site
  * died without going through libc's __GI__exit thunk

Candidates for the M9.R.64 attribution phase (not addressed here):

  * clone3 / vfork with CLONE_VFORK where the child issues an inline
    `syscall #execve` before the shim init runs (would show
    `phase=init` in current diag), and the exec image is
    similarly-hooked but a different process
  * A different exit family: SYS_exit vs SYS_exit_group when called
    from a thread inside a threaded builder
  * Signal delivery on the WRONG thread (main-thread handler
    installed, but a worker calls _exit through a pre-existing
    signal disposition inheritance) — SIGKILL on a non-main thread
  * A subprocess that unmaps librepro_monitor_shim.so (dlclose)
    before exiting, so all our hooks are gone
  * dlopen of a fresh non-io-mon-hooked libc handle (RTLD_DEEPBIND
    or explicit libc.so.6 dlopen from a nix wrapper) whose _exit
    then does inline syscall

Diagnostic path forward (deferred to M9.R.64):
  1. Add per-escapee last-fd + last-record-address to the diag ctx
  2. Run under strace -f -e trace=exit_group,exit,execve,tgkill
     for a single failing process to see the kernel-level shape
  3. Inspect a single dying process's /proc/PID/maps to see what
     mappings were loaded (potentially fresh dlopen of libc.so.6)
  4. Inspect the raw fragment on-disk to see the LAST record kind
     before the kill

None of these require a new architectural workstream. All are
observation-only diagnostics that will pin the escape shape
unambiguously — same recipe as M9.R.62.1's diag-ctx sampling.
