The M9.R.63 fix shape (Shape B, per the plan taxonomy)
------------------------------------------------------
The mechanism EXISTS in nim-stackable-hooks AND io-mon consumes it. The
residual gap is in io-mon's mapping-eligibility POLICY at:

  src/io_mon/hooks/linux_preload_runtime.nim
    proc isSystemRuntimeMappingPath(path: string): bool =
      ## Keep startup DSO scanning out of loader/libc/toolchain runtime
      ## mappings.
      path.startsWith("/lib/") or path.startsWith("/lib64/") or
        path.startsWith("/usr/lib/") or path.startsWith("/usr/lib64/") or
        path.startsWith("/nix/store/")            <-- LOAD-BEARING LINE

The pixman `__repro_provider_compile` workload (M9.R.62.3 + M9.R.62.3b
attribution) is a nix-built toolchain (cc-wrapper, wrapped-sh,
add-hardening.sh, bash-invoked shells) whose EVERY executable and
application-owned DSO lives under /nix/store/. So even though io-mon
scans its own main-executable, /nix/store/-hosted binaries have their
main-executable AND their application DSOs excluded by the CURRENT
policy — including any workload binary that issues an inline
`syscall #exit_group` from a nix-built .so or a nix-built static exec.

M9.R.62 concluded the escape shape was "INLINE-ASSEMBLY raw
`syscall #exit_group` / `syscall #exit` issued from user code" and
proposed seccomp-BPF as the fix. Per user pushback, the correct fix is:

  Refine `shouldPatchInlineSyscallMapping` so it patches ANY mapping
  whose normalized path matches the CURRENT-PROCESS EXECUTABLE PATH,
  regardless of whether that path is under /nix/store/, and also
  patches nix-store-hosted application binaries and their non-runtime
  application DSOs. Keep the loader / libc / dynamic-linker runtime
  exclusion (glibc / musl / libpthread / libdl / ld-linux.so) to avoid
  making a nix-hosted glibc's `syscall(2)` wrapper INT3-scan itself.
