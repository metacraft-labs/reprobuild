Phase A summary — typed-tool call-site audit
---------------------------------------------
Full audit lives in
``recipes/reproos-image/run-evidence/m9r79/m9r79_phaseA_typed_tool_audit.txt``.

Key finding: the typed-tool wrapper procs generated by macros_a.nim's
schema emitter route through ``recordToolInvocation`` → ``recordCommandAction``
→ ``buildAction`` with a fixed formal-parameter surface.  Threading two
new params through that macro would touch every ``executable ... cli:``
schema in the corpus (dozens of typed tools) plus every downstream call
site (hundreds of recipes).

Design chosen: post-emit REGISTRY MUTATORS mirroring the M9.R.14e.5
pattern for ``appendRegisteredActionToolIdentityRefs``.  Two new procs
in ``libs/repro_project_dsl/src/repro_project_dsl/runtime_core.nim``:

  * ``setRegisteredActionDeclaredOutputs(actionId, outputs)``
  * ``setRegisteredActionReadOnlyRoots(actionId, roots)``

Semantics: locate the registry entry by id (linear scan — registry
is small at recipe-eval time), assign the entire seq (SET not APPEND
because each edge has one write scope known at construction time).
No-op when the id is not present (defensive — same shape as
``setRegisteredActionTargetNames`` /
``appendRegisteredActionToolIdentityRefs``).

Threading site count per constructor:
  * meson_package: 3 edges (setup / compile / install) — all typed-tool.
  * autotools_package: 4 edges (configure / make / make install /
    la cleanup).  Configure + la cleanup use direct ``buildAction()`` so
    the fields are added inline; the two ``make`` edges use the setters.
  * cmake_package: 3 edges (configure / build / install).  Configure is
    typed-tool so uses setters; build + install were converted to direct
    ``buildAction()`` in M9.R.14g.6 (cmake doesn't accept ``build``/
    ``install`` as subcommand literals), so those take the fields inline.


Phase B / C / D summary — constructor threading
------------------------------------------------
Every constructor edge now declares:

  * ``declaredOutputs``: the write ROOT (buildDir for configure /
    compile, DESTDIR / effectiveDestRoot for install).  Sequential
    edges via the ``deps``/``after`` chain share the same buildDir
    scope; R7's dep-chain relaxation (M9.R.75.3.1) exempts them.

  * ``readOnlyRoots``: the upstream source tree (``<projectRoot>/srcDir``
    when provider mode is active; falls back to the relative form in
    unit-test mode so existing tests stay byte-identical).

Autotools has one carve-out: when ``patchHardcodedFile = true``, the
bootstrap runs ``autoreconf -fi`` inside srcDir which legitimately
regenerates files there.  In that mode ``readOnlyRoots`` is empty per
R6's "action explicitly owns the target location" exception
(Filesystem-Policy-And-Observed-Inputs.md line 268).

Absolute-path resolution uses ``activeProviderProjectRoot()`` when
available so the enforcement layer sees the same shape the file
monitor emits (absolute host paths).  Unit-test mode falls back to
the relative form so existing tests stay byte-identical.


Phase E summary — $OUT_MIRROR env-var mechanism
------------------------------------------------
Landed as one small edit to
``libs/repro_standard_provider/src/repro_standard_provider/conventions/
from_source_custom.nim``'s ``emitShellActions``: the DSL emitter now
adds ``("OUT_MIRROR", outMirrorRoot)`` to every shell action's ``env``
seq at emit time.  The value shape matches
``types/package_result.emitInstallTreeMirror``'s ``dstUsrRoot`` local:
``<projectRoot>/.repro/output/install``, POSIX-slashed.

No engine-side plumbing was needed — the existing per-action ``env``
slot already flows through ``launchChildEnv``, and the runquota /
non-runquota fork paths both pick up the entry via ``action.env``'s
loop at ``repro_build_engine.nim:2681``.

The value is constant per-recipe (mirror root is a recipe property,
not an action property) so it does not perturb the action-cache
fingerprint.  Different recipes running side-by-side see different
OUT_MIRROR values.

Verified: test_from_source_custom_convention (11 assertions) still
passes after the env addition.


Phase F summary — recipe migrations
------------------------------------
Migration count: 1 LIVE (hwdata).

Breakdown of the 11 recipes flagged in M9.R.76.5:

  MIGRATED (1):
    * hwdata (commit 0f8462e8): replaced the host-relative
      ``MIRROR=$(cd $extracted/.. && pwd)/.repro/output/install``
      shell-block resolution with ``MIRROR=${OUT_MIRROR}``.  Removes
      the brittle ``$extracted/..`` traversal.  Emitted shell command
      is byte-identical to pre-M9.R.79 once the env variable
      substitutes.

  DEFERRED — sibling-recipe references (2):
    * qt6-quickcontrols2: hardcodes SIBLING recipe paths
      (``../qt6-declarative/.repro/output/install/usr``), not its own
      recipe's mirror.  These need the M9.R.76 install_mirror_resolver
      surface plumbed via ``extraEnv`` (or a per-dep ``DEP_<name>_ROOT``
      env-var mechanism analogous to $OUT_MIRROR) rather than
      $OUT_MIRROR.  Documented as a follow-up milestone.
    * kwin: hardcodes ABSOLUTE Linux paths
      (``/opt/repro/reprobuild/recipes/packages/source/wayland/...``)
      to sibling recipes for CMAKE_{C,CXX}_FLAGS include-path
      threading.  Same class as qt6-quickcontrols2 — needs a sibling-
      recipe env-var mechanism.  Deferred.

  DOCSTRING-ONLY REFERENCES — no live impact (8):
    * plasma-workspace (line 379: example ``ls`` in comment).
    * xtrans (lines 47-48).
    * xorgproto (line 48).
    * iana-tzdata (line 84).
    * breeze (line 95).
    * ksolid (lines 138-139).
    * plasma-wayland-protocols.
    * extra-cmake-modules.

    These are pure documentation references to the physical output
    location; the raw path is factually accurate today (the resolver's
    ``immLegacy`` mode returns the same path).  A future comment sweep
    could rephrase them as "the canonical install-mirror root
    (see install_mirror_resolver.nim)" without changing behaviour;
    deferred to avoid churn.
