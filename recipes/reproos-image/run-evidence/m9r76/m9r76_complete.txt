User directive
--------------
"reprobuild-specs R10 defines install-mirrors as content-hashed
side-by-side prefixes (per output-set hash), NOT stable per-recipe

stable mutable filesystem path — a load-bearing architectural gap
surfaced across M9.R.60-70. This is a multi-week refactor. Focus on
landing the design + core mechanism in this milestone; leave migration
of existing recipes as documented follow-up if scope grows."

Addendum to Store-And-Installation-Layout.md §R10
--------------------------------------------------
Three normative sub-sections added:

  * "Realization Hash Inputs (normative)" — the canonical BLAKE3-256
    envelope:
      1. package name + version
      2. source acquisition identity (tarball SHA-256 / commit id)
      3. resolved dep (name, hash) list
      4. resolved options
      5. target platform / ABI
      6. toolchain identity
      7. env-normalization identity

  * "Legacy Fallback (transitional)" — the engine SHOULD support a
    resolver that returns the mutable path when the content-hashed
    prefix does not exist yet; driven by an opt-in env var. Removed
    once every first-party recipe is migrated.

  * "Read-Only Enforcement (post-publish)" — the prefix contents MUST
    be read-only via mode bits or sandbox policy; peer-recipe writes
    fail-closed as a double-write violation per R7.

Phase B — engine + DSL core mechanism
======================================

Implementation site
-------------------
libs/repro_dsl_stdlib/src/repro_dsl_stdlib/types/install_mirror_resolver.nim
(148 lines; new file).

Public API
----------
  currentInstallMirrorMode() -> InstallMirrorMode
      Reads $REPRO_INSTALL_MIRROR_MODE (legacy / hashed /
      hashed-with-legacy-fallback); unset falls back to legacy.

  packageInstallMirrorRoot(recipesRoot, depName) -> string
      Returns the dep's install-mirror root POSIX-slashed.

  packageInstallMirrorLibDirs(recipesRoot, depName) -> seq[string]
      Returns [usr/lib, usr/lib64] under the resolved root.

  packageInstallMirrorPkgConfigDirs(...) -> seq[string]
      Returns [usr/lib/pkgconfig, usr/lib64/pkgconfig,
      usr/share/pkgconfig].

  packageInstallMirrorCmakeRoot(...) -> string
      Returns <mirror>/usr/lib/cmake.

  packageInstallMirrorIncludeDir(...) -> string
  packageInstallMirrorPropagatedManifestPath(recipesRoot, dep, manifestFile)
  packageInstallMirrorHumanFriendlyPath(...) -> string
      Always-legacy shape for diagnostic messages that must be
      stable across mode switches.

Phase D — read-only enforcement (M9.R.76.4)
============================================

Implementation
--------------
emitInstallMirrorReadOnlyEnforcement(mirrorRoot, mode) in
install_mirror_resolver.nim. Semantics:

  immLegacy:                        returns "" (the mutable stable
                                    path MUST stay writable).
  immHashed:                        emits ``chmod -R a-w`` on the
                                    mirror root, guarded by
                                    ``[ -d ... ]``.
  immHashedWithLegacyFallback:      emits ``chmod -R a-w``.

installMirrorEnforcesReadOnly(mode) — companion predicate for
plan-time callers.

Wired into emitInstallTreeMirror after the touch stamp; recipes that
opt into hashed mode automatically get read-only enforcement without
any recipe-side change.

Regression coverage (6 new assertions):
  * legacy mode emits empty snippet
  * hashed mode emits chmod -R a-w
  * hashed-with-legacy-fallback enforces read-only
  * empty mirror root produces empty snippet (defensive)
  * explicit mode arg overrides env var (plan-time control)
  * shell path escapes preserve double-quote safety

Deferred: the actual EROFS regression test — a deliberately-buggy
test recipe that tries to touch a peer recipe's published prefix —
needs the recipe DSL to declare ``useHashedMirror = true`` at recipe
scope. That per-recipe knob is Phase 2 of the migration (M9.R.77+)
and gated on the emit-side wiring landing.

Honest residuals
================

1. **Migration is incomplete by design.** M9.R.76 landed the core
   mechanism (spec addendum + resolver + 6 threading sites +
   read-only enforcement gating + 1 recipe migration). The bulk of
   the recipe corpus (11 hardcoded live sites + doc-only references)
   is documented as follow-up work. The user directive explicitly
   scoped this milestone to "landing the design + core mechanism";
   deferring recipe migration is on-plan.

2. **Emit-side hashed-mode wiring not landed.** The resolver's
   ``immHashed`` branch currently falls back to the legacy path
   because ``hashedDepMirrorRoot`` returns "" (no recipe has opted
   in via a per-recipe ``useHashedMirror = true`` DSL knob yet).
   The knob + the emit-side realization-hash computation + the store-
   registration write path are Phase 2 of the migration; the resolver
   contract is already stable so those additions won't require
   changing any of the 6 threading sites.

3. **Realization-hash computation deferred.** The spec addendum's
   normative hash-input list is authoritative but the engine-side
   implementation of ``computeInstallMirrorHash(BuildActionDef)``
   is not landed. That's blocked on the M9.R.74 canonical-execution-
   root work (R2) settling — the hash includes the "env-normalization
   identity" which depends on R2's environment-normalization pass
   being stable.

4. **Read-only enforcement is emit-side only.** The engine-side
   sandbox-policy layer that would enforce EROFS on the FS-monitor
   backend is deferred; today's enforcement is mode-bits only. The
   spec addendum §"Read-Only Enforcement" §2 (sandbox policy backend)
   is the follow-up landing site.

5. **No cross-agent contention regression tests.** The mid-milestone
   sub-agent-collision noted below was benign (correct code landed
   under mislabeled commit titles) but exposed a workspace hygiene
   issue that should be tracked separately.


Cross-agent collision note
==========================

During this milestone a parallel sub-agent was landing M9.R.73 and
M9.R.74 commits (canonical execution root + narrow monitor-loss
invalidation). The pre-commit hook environment on Windows silently
mixed staged tree contents between sub-agents:

  * origin/dev's commit ce00ee16 (titled "M9.R.76.2: DSL install-mirror
    resolver — spec R10 core mechanism") actually contains M9.R.74.4
    from_source_custom.nim work.
  * origin/dev's commit 47837fe7 (titled "M9.R.74.5: close-out")
    actually contains MY M9.R.76.2 resolver + package_result.nim +
    t_m9r76_install_mirror_resolver.nim files.

The M9.R.74 sub-agent documented this in their close-out. Content is
correct on both sides; commit-message log is misleading for two
specific SHAs. The M9.R.76.3 / .4 / .5.1 / .6 commits landed cleanly
after the collision resolved.

This documents the honest git-log state for future readers.
