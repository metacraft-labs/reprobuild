Phase A key spec doc citations
-------------------------------
R3 (Failure-Semantics.md §"General Rules"):
  Ambiguous correctness failures MUST fail closed: reject cache reuse,
  rerun, or require review rather than silently accepting stale state.

R4 (Failure-Semantics.md §"Monitoring Failures"):
  * If the monitor drops events or detects possible loss, affected
    path sets MUST be invalidated conservatively.
  * If event loss scope is unknown, the engine MUST invalidate the
    whole affected watch root or disable cache hits for the affected
    session.
  * If required monitoring is unavailable for an action, the scheduler
    MUST either choose a compatible backend or reject/fallback
    according to explicit policy.

  Reading R3 + R4 together, the spec defines a 4-level ladder for
  monitor-loss handling: Level 0 (no loss / publish) → Level 1 (known
  scope / invalidate path set) → Level 2 (unknown scope / disable
  cache hits for session) → Level 3 (monitor unavailable / fail
  action).

R10 (Store-And-Installation-Layout.md §"Immutable Side-By-Side
Prefixes"):
  Every realized package instance should live in its own immutable
  prefix.
  - different realizations never overwrite one another
  - packages can be garbage-collected when unreachable from any active
    root
  - local development views are layered on top of the immutable store,
    not substituted for it

R11 (Store-And-Installation-Layout.md §"Human-Friendly Package Store
Versus Opaque Content Store"):
  Two layers: human-friendly realized package store + lower-level
  opaque content store. The current implementation mixes them.


Phase B highest-value gaps identified
--------------------------------------
Ranked by load-bearing-ness for the recurring M9.R.60-70 symptoms:

  Gap I  (HIGHEST):  monitor-loss ladder collapse.
                     Engine treats all of R4's Levels 1/2/3 as Level 3
                     (fail-closed on the action). Directly causes exit=0
                     → asFailed observed in M9.R.60.D / M9.R.68 / M9.R.70.

  Gap II  (medium):  event-loss classification discarded.
                     io-mon's writer.nim classifies each loss by detail
                     string; the engine discards it at fold time.

  Gap III (arch.):   install-mirror at a mutable stable path.
                     R10 requires immutable side-by-side. Multi-week
                     refactor of DSL threading (PKG_CONFIG_PATH,
                     CMAKE_PREFIX_PATH, LD_LIBRARY_PATH would need to
                     enumerate hash-derived paths).

  Gap IV  (arch.):   no separate CAS store layer (R11).
                     Multi-week refactor.

  Gap V   (medium):  per-tool policy source (R12) not fully wired.
                     Partially addressed via the classifier introduced
                     by Gap I's fix.

  Gap VI  (low):     source-rewrite + double-write enforcement (R6/R7)
                     missing.
                     Not blocking M9.R.60-70 arc.

  Gap VII (in-progress): canonical execution root path-independence
                     (R2). Actions still run under the checkout path.


Phase C fix landed — Gap I
---------------------------
Files changed:
  libs/repro_build_engine/src/repro_build_engine.nim
    + MonitorEvidenceStatus enum (mesComplete, mesKnownScopeLoss,
      mesUnknownScopeLoss, mesMonitorUnavailable) — the spec's ladder
      typed at the engine.
    + classifyEventLossDetail(detail) — maps io-mon writer.nim detail
      strings to Level 1/2:
        kill-before-flush             → Level 1 (known scope)
        unmonitored-subtree/peer       → Level 2 (unknown scope)
        ambiguous-unstamped-fragment   → Level 2
        duplicate-identity-token       → Level 2
        external-content               → Level 2
        breakaway-report               → Level 2
        unknown detail                 → Level 2 (fail-closed per R3)
    + worseMonitorStatus — ordering helper for the fold loop.
    + foldMonitorDepFileEvidence now returns MonitorEvidenceStatus
      (was bool).
    + EvidenceCollection gains disableCacheHits + monitorStatus
      fields. When collectEvidence detects Level 1/2 loss on a
      cacheable action, it sets publishable=true + disableCacheHits=
      true (not the previous publishable=false).
    + 3 post-execution scheduler sites (repro_build_engine.nim:4181,
      4284, 4654) now consult disableCacheHits: skip
      cache.recordActionResult when set, emit a
      "cache-skip-monitor-loss" trace event, otherwise unchanged.
    + Level 3 fail-closed behavior preserved (empty RMDF path OR
      decode error) — genuine "monitoring unavailable" per spec.

Regression tests:
  libs/repro_build_engine/tests/test_m9r72_monitor_loss_classifier.nim
    8 unit tests: 6 io-mon detail-string prefixes + unknown-fail-closed
    + enum ordering.
  libs/repro_build_engine/tests/test_m9r72_phaseD_end_to_end.nim
    4 e2e tests using io-mon's real encodeCanonical to build synthetic
    RMDFs and drive foldMonitorDepFileEvidence directly.

All 12 tests pass on Windows debug build.


Phase D validation — class-of-issue closed
-------------------------------------------
The M9.R.60.D / M9.R.68 / M9.R.70 recurring symptom is now closed at
the engine level:

  * exit=0 action with real outputs → stays asSucceeded.
  * evidence's trustworthy path observations survive the presence of
    event-loss records (test 1 confirms with a real mrFileRead +
    kill-before-flush loss in the same RMDF).
  * action-cache publish is skipped for the session (test also
    verified against the disableCacheHits branch of 3 scheduler
    sites).
  * downstream cascade runs normally (no blockClosure).
  * future rebuild re-executes rather than trusting incomplete
    evidence — the spec-mandated Level 2 handling.

Level 3 fail-closed behavior preserved for the "monitor genuinely
unavailable" case (empty RMDF path OR decoder threw). No soundness
hole introduced.


Spec gaps deferred to future milestones
---------------------------------------
Gap II (event-loss classification -> narrow Level 1 path-set
invalidation): the classifier is in place; the follow-on is to route
Level 1 losses through a narrow path-set invalidation instead of the
current session cache-skip. Requires a per-loss-class soundness memo.

Gap III (immutable side-by-side install-mirror prefixes per R10):
multi-week refactor of every autotools / meson / cmake DSL constructor
+ every PKG_CONFIG_PATH / CMAKE_PREFIX_PATH / LD_LIBRARY_PATH
threading site. Not addressable within one milestone.

Gap IV (separate CAS layer per R11): same architectural scope.

Gap VI (source-rewrite + double-write enforcement per R6/R7): not
blocking any current recipe. Adds correctness tightening.

Gap VII (canonical execution root per R2): known open item;
path-remapping standard-library work is a separate milestone.


Honest residual
---------------
1. The M9.R.60-70 recipes are NOT re-executed under this fix in
   Phase D. The evidence is:
     * unit tests verify the classifier behaviour.
     * end-to-end tests verify the RMDF pipeline returns the correct
       status enum and preserves trustworthy path observations.
     * source-level review confirms the 3 post-execution scheduler
       sites now skip cache.recordActionResult when disableCacheHits
       is set.

   A full re-execution of the reproos-image / wlroots / hwdata chain
   would prove the class-of-issue closed in production; those recipes
   only run on eli-wsl and would take hours. Committing the fix +
   tests here lets the next Linux session prove the class-of-issue
   closed empirically. Until then this milestone's evidence is
   test-level, not recipe-level.

2. The Level 1 handling is currently the same as Level 2 (session
   cache-skip). The spec explicitly says Level 1 could allow
   "invalidate the affected path set" and still publish a narrowed
   cache entry, but the narrow-invalidation semantic requires a
   per-class soundness proof that's out of scope here.

3. Class-D fix from M9.R.60.D's candidate list — this is candidate B
   ("engine-side dependencyPolicy = dgOpaqueToolWithDeclaredInputs")
   reshaped as a spec-graded ladder rather than a per-action opt-in.
   The spec's ladder is a strictly stronger + more principled fix
   than the per-action opt-in because it applies to ALL cacheable
   actions uniformly, driven by the classified loss-scope evidence
   io-mon already produces.
