Finding 1 — reproos-image doesn't cascade dep builds
-----------------------------------------------------
`recipes/reproos-image/repro.nim`'s `extraInputs` lists only static
paths (build script, auto-config fixture, three reused staging
helpers). The reproos-image action is a single shell action that
runs `stage-de-rootfs.sh` which merely MIRRORS existing
`.repro/output/install/` trees; it does NOT recursively drive
per-recipe builds.

So `repro build recipes/reproos-image` alone cannot rebuild
hwdata / libdisplay-info / wlroots / sway. Each from-source recipe
must be built independently first (as M9.R.58/59's `_m9r59_build_*.sh`
harness scripts did). This is not a Phase D fault — it's a
preexisting reproos-image recipe design: DE recipes are declared as
independent buildable units, not transitively wired via extraInputs.


Finding 2 — the fetch-action gate IS closed
--------------------------------------------
After the M9.R.60.2/3 fixes landed, `ccpp-fetch-<recipe>` actions
no longer surface the "monitor depfile is incomplete" diagnostic.
Class M9.R.60.1 is closed.


Finding 3 — a SECOND gate hides behind the fetch gate
------------------------------------------------------
Both hwdata AND pixman (baseline control test — the recipe M9.R.60.1
Phase A also used) FAIL on a DIFFERENT action:

  daemon-hosted build failed: __repro_provider_compile asFailed
  monitor depfile is incomplete

`__repro_provider_compile` is the recipe DSL provider-compile edge —
runs reprobuild's OWN `nim c` of the recipe's provider binary
(`repro_cli_support.nim:3493`). Not the fetch action.

RMDF inspector output (`m9r60_phaseD_pixman_rmdf_header.txt`):

  RMDF version=1 records=251136 completeness=mcIncomplete
  ... 182 event-loss records with detail=`process killed with an
  un-flushed read batch (kill-before-flush)` ...
  summary records=251136 processes=838 observations=250954
    eventLoss=182

Root cause: `nim c` spawns ~838 subprocesses (bash / cc-wrapper /
clang / ld / gcc-libgcc / coreutils rm). 182 of them exit through
paths that escape the io-mon Linux preload shim's `_exit` / `execve`
flush hooks (io-mon commits f428b9b + 451eb2d). Each escaped exit
leaves a `read-tail-pending` sentinel un-committed. `mergeFragments`
(writer.nim:1673) fabricates 182 synthetic `mrEventLoss` records →
`completeness=mcIncomplete` → `foldMonitorDepFileEvidence` returns
false → "monitor depfile is incomplete" diagnostic → action asFailed.

M9.R.60.2's non-cacheable carve-out doesn't apply here because
`__repro_provider_compile` is `cacheable = true` BY DESIGN — the
in-code comment at `repro_cli_support.nim:3485-3492` explicitly
rejects a prior `dgNoRuntimeDependencies` downgrade as "an
unapproved soundness hole".

Candidate follow-up work for closing Class M9.R.60.D
-----------------------------------------------------
Documented in `m9r60_phaseD_characterization.txt`. Ordered from
most-conservative to least:

  A. io-mon-side: close the Linux kill-before-flush pathway via a
     SIGCHLD-side supervisor (round-2 sidecar-file mechanism was
     retired for tamper-resistance; needs a tamper-resistant
     replacement).

  B. reprobuild-engine-side: add per-action opt-in policy
     `dgOpaqueToolWithDeclaredInputs` that permits `mrEventLoss`
     inside spawned children of a specific opaque tool when the
     top-level action's declared inputs + weakFingerprint fully
     cover the cache key. `__repro_provider_compile` already
     carries a `plan.compileEdge.actionFingerprint` weakFingerprint
     that encodes reprobuild's pinned libs closure.

  C. Recipe-side: declare `dependencyPolicy = declaredOnlyPolicy()`
     for `__repro_provider_compile`. REJECTED upstream at
     `repro_cli_support.nim:3488-3492` as "an unapproved soundness
     hole". Not viable.

  D. io-mon-side workaround: downgrade the `mcIncomplete` seal to
     `mcComplete` when the ONLY loss records are kill-before-flush
     markers AND the un-flushed child was an inner compile-driver
     (nim c / gcc / clang / ld). Same soundness tradeoff as B but
     in io-mon rather than reprobuild.
